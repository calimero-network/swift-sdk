Instead of polling, subscribe to a context's real-time events. `mero.events(contextIds:)`
opens a Server-Sent-Events stream and yields a `ContextEvent` for each emission —
new messages, application-version flips, and other context activity — so a view
can react as changes arrive.

## Subscribe

`events(contextIds:)` returns an `AsyncThrowingStream<ContextEvent, Error>`.
Consume it with `for try await`, inside a `Task` you can cancel:

```swift
let task = Task {
    do {
        for try await event in mero.events(contextIds: [contextId]) {
            switch event.kind {
            case "StateMutation":
                await reloadMessages()
            case "SyncStatus":
                print("syncing: \(event.payload)")
            default:
                print("event on \(event.contextId): \(event.kind)")
            }
        }
    } catch {
        // the stream ended with an error (e.g. auth lost)
    }
}
```

Each event is:

```swift
public struct ContextEvent: Sendable {
    public let contextId: String
    public let kind: String        // "StateMutation" or "SyncStatus"
    public let payload: JSONValue  // raw event JSON
}
```

`kind` is the frame's `result.type`, and a node sends exactly two:
**`StateMutation`** (the context's state moved) and **`SyncStatus`**
(`syncing` / `waitingForPeers` / …). There is no `ExecutionEvent` — a `case` for
one never fires.

The contract's own events are nested a level down, under `payload`'s
`data.events[]`, each with its **own** `kind` and a `data` byte array carrying
the encoded event. Captured from a live 0.11.0-rc.32 node:

```json
{"result":{"contextId":"…","type":"StateMutation","data":{
  "newRoot":"7320c55a…",
  "events":[{"kind":"Inserted","data":[123,34,107,…],"handler":null}]}}}
```

So the frame tells you *that* state moved and the nested `events[]` tell you
*what* the contract emitted.

## Reconnection

The stream reconnects automatically after a drop and re-subscribes your ids on
the new session. You don't need to rebuild the stream on a transient network
blip — the `for try await` loop keeps delivering events across reconnects.

The first reconnect waits 3 seconds (mero-js's `reconnectDelayMs`). While the
node keeps refusing or stays unreachable, each further attempt doubles the wait
up to 30 seconds, with ±20% jitter so a fleet of clients does not retry in
step; once a stream opens, the next drop waits 3 seconds again. Pass
`backoff: .fixed(3)` to `SseClient` / `SseConnection` for mero-js's flat delay.

A `403` — or a `401` whose `x-auth-error` names a dead token family — is
terminal: the stream finishes with that `MeroError` instead of retrying a
credential that can never work.

## One connection, changing subscriptions

Each `mero.events(...)` call opens its own connection for a fixed set of ids.
To add and drop contexts while one connection runs — a chat list whose rooms
come and go — use the instance's shared `mero.sse`:

```swift
let sse = mero.sse
sse.connect()
try await sse.subscribe(contextIds: [roomA])
try await sse.subscribe(contextIds: [roomB], groupIds: [team])
try await sse.unsubscribe(contextIds: [roomA])
sse.isSubscribed(roomB)   // true

for try await event in sse.events() { … }
```

`subscribe` and `unsubscribe` send only what changed, to the live session
(`POST /sse/subscription`, 10 s timeout). Every remembered id is re-subscribed
after a reconnect, and `.connect(sessionId:)` on `sse.updates()` is announced
once that has landed.

## Typed events

```swift
for try await change in mero.appVersionChanges(contextIds: [contextId]) {
    print(change.fromVersion ?? "?", "→", change.toVersion ?? "?")
}

for try await migration in mero.migrationEvents(groupIds: [namespaceId]) {
    switch migration {
    case .migrationStarted(_, let started): print("to", started.toVersion)
    case .migrationProgress(_, let progress): print(progress.migrated, "/", progress.total)
    case .cascadeProgress(_, let cascade): print(cascade.subgroupId)   // admins only
    case .migrationCompleted(_, let done): print("done at", done.completedAt)
    }
}
```

On a shared connection the same are `sse.appVersionChanges()`,
`sse.migrationEvents()`, `sse.membershipEvents()`, and the callback forms
`sse.onAppVersionChanged { … }` / `sse.onMigrationEvent { … }`, which return
the closure that removes the handler.

## Closing the stream

The stream's lifetime is owned by the `Task` consuming it — **cancel that task**
to close the SSE connection:

```swift
task.cancel()   // closes the connection
```

<Aside type="note">
  `mero.close()` and `mero.logout()` end every event stream the instance
  started. For a stream tied to one screen, still start the loop in `.task { }`
  so SwiftUI cancels it when the view disappears.
</Aside>

## In SwiftUI

`.task` ties the stream to a view's lifetime — it's started when the view
appears and cancelled automatically when it disappears:

```swift
struct MessagesView: View {
    let contextId: String
    @State private var messages: [Message] = []

    var body: some View {
        List(messages) { Text($0.text) }
            .task {
                do {
                    for try await _ in mero.events(contextIds: [contextId]) {
                        messages = await load()
                    }
                } catch { /* stream ended */ }
            }
    }
}
```

<Aside type="note">
  `events(contextIds:)` is `nonisolated`, so you can call it without `await`; it
  reads the token lazily when it connects.
</Aside>
