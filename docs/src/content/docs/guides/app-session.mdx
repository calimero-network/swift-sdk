`MeroAppSession` (MeroKitUI) is an app's signed-in account. Its `backend`
(`any MeroAppBackend`, a `CloudAppBackend` when signed in) is what screens
use; tests hand view models `InMemoryAppBackend` instead.

```swift
@StateObject var session = MeroAppSession(
    packageName: "com.calimero.chat", callback: .scheme("merochat", path: "consent"),
    config: MeroProviderConfig(nodeURL: "https://node.example"))
```

| Member | |
| --- | --- |
| `restore()`, `signIn()`, `signUp(name:)`, `signOut()`, `connect(nodeURL:allowMock:)` | sign-in |
| `backend`, `revision`, `isSignedIn`, `account`, `applicationId`, `contract` | state |
| `handle(url)`, `pendingInvitation`, `redeemPendingInvitation()`, `createInvitationLink(namespaceId:)` | invitations |
| `pendingApprovals(org:)`, `requestConsent(_:)` | approvals |

## Names

The backend keeps the names it had before 1.0; each is one 1.0 concept:

| App layer | Calimero 1.0 |
| --- | --- |
| namespace | organization (founded with metadata `{name, package}`) |
| subgroup | team (`isPublic` → `join: everyone`) |
| context | app instance (its app id) |
| application | package |
| `query` / `execute` | `POST /apps/{app}/views` / `intents` |
| invitation (`OrgInvitation`, alias `SignedGroupOpenInvitation`) | invite token `inv_…` |
| `hasRelay`, `canSubscribe` | always `true` once signed in |

`createContext(groupId:applicationId:name:initArgs:service:)` names one service
of a multi-service package. `CloudAppBackend.client` is the full `CalimeroClient`.

## Invitation links

`https://links.calimero.network/<package>/join?invitation=<base58(deflate(json))>`,
the JSON being `InvitationLinkPayload`:

```json
{"invitation":{"orgId":"…","token":"inv_…"},"namespaceId":"…","contextId":"…"}
```

## Tests

`MeroKitTestSupport` has `InMemoryAppBackend` and `RecordingContextContract`
for view models, and `FakeCloudNode` + `FakeCloud` for the whole stack: a node
that runs the real sealed channel and mock attestation, and an in-memory
cluster behind it.
